  • 空文字のみエラー。空白のみの入力、文字種、最小／最大桁数の検証は未実装。

1.3 現状の課題

No課題影響
1空白のみの入力でも必須チェックを通過する不要な認証リクエストが発生する
2文字種の制限がない（全角・日本語・絵文字などが入力可能）後続のユーザー管理・API 連携時に不整合が起きる
3trim() をパスワードに適用している前後空白を含む正当なパスワードが認証失敗する
4maxLength={32} による無言の切り捨て33 文字目以降が入力できず、入力誤りに気付けない
5ユーザー管理画面のパスワード欄は通常の Input（平文表示）画面間でコンポーネント・ルールが不統一
6react-ud（Login_内部設計.md）と検証方式が異なるプロジェクト間で仕様が分岐する

2. 検証ルール（To-Be）

2.1 ルール一覧

No 検査項目 検査タイミング 検査条件 エラーメッセージ 動作
1 必須 入力時（onChange）／送信時 未入力、または空白のみ（trim() 後に空） パスワードを入力してください。 送信中断（API 呼出なし）
2 最大桁数 入力時（onChange）／送信時 50 文字を超える パスワードは50文字以内で入力してください。 送信中断
3 文字種（許容） 入力時（onChange）／送信時 半角英数字および ASCII 記号（0x21〜0x7E）以外を含む パスワードは半角英数字と記号で入力してください。 送信中断
4 最小桁数 ― ログイン画面では検査しない ― ―
5 認証結果 送信時（API 応答後） ユーザーID またはパスワードが不一致 ユーザーIDまたはパスワードが正しくありません。 エラー表示、画面遷移なし
補足
  • ログイン画面の検証は「形式チェック」のみとし、パスワード強度（英大文字・小文字・数字・記号の組み合わせ、8 文字以上など）の検査は行わない。理由は 2.2 のとおり。
  • 認証失敗時のメッセージは、ユーザーID の存在有無やパスワード規則を推測されないよう曖昧な表現に統一する。

2.2 最小桁数を設けない理由

  1. 既存ユーザーの中に短いパスワードのアカウントが存在する可能性があり、ログイン時に弾くと正当なユーザーがログイン不能になる。
  2. ログイン画面で桁数下限を提示すると、パスワードポリシーが外部に漏れる。
  3. 桁数下限は「新規登録／パスワード変更」画面でのみ適用するのが一般的な設計である。

3. 文字種の定義

3.1 許容文字

区分対象備考
半角英字A-Z、a-z―
半角数字0-9―
ASCII 記号 ! " # $ % & ' ( ) * + , - . / : ; < = > ? @ [ \ ] ^ _ ` { | } ~ 表示可能な ASCII 記号（0x21〜0x7E）

3.2 禁止文字

区分例備考
全角文字ａ １ あ ア 漢IME 経由の入力を含む
空白類半角スペース、全角スペース、タブ前後空白も許容しない
制御文字改行、0x7F、0x00〜0x20―
マルチバイト記号・絵文字￥ 〜 😀―

3.3 正規表現

ホワイトリスト方式（ブラックリスト方式は使用しない）を採用する。

/^[\x21-\x7E]+$/

補足：0x21〜0x7E は「半角英数字＋ASCII 記号」と「空白・制御文字を含まない」を同時に満たす。

4. 実装方針

4.1 コンポーネント

項目方針
コンポーネントInput.Password を継続使用（マスク表示・表示切替は既定のまま）
autoCompletecurrent-password を維持
maxLength50 を維持（保険としての上限。単独でエラーを表現しない）
表示切替visibilityToggle は既定（有効）とする

4.2 検証の実装分担

役割実装方法内容
入力の制限（サニタイズ） 実施しない 入力自体は制限せず、許容外の文字は rules でエラー表示する
エラー表示Form.Item の rules必須・最大桁数・文字種の 3 ルール
検証タイミングantd 既定の onChange（入力時）＋送信時入力中も即時にエラーを表示する（validateTrigger は指定しない）
照合onFinish 内パスワードは加工せずそのまま送信する

4.3 パスワードの取り扱い

No方針理由
1パスワードに対して trim() を行わない前後空白は仕様上禁止（第 3 章）であり、加工すると認証結果が変わる恐れがある
2ユーザーID のみ trim() する入力補助として妥当。パスワードとは扱いを分ける
3normalize() などの文字列正規化を行わないパスワードの意味が変わる
4パスワードをログ出力・localStorage 保存しないセキュリティ要件

4.4 ユーザー管理画面との統一

User/UserManagementScreen.tsx のパスワード欄は Input.Password に変更し、共通の validatePassword() で保存前に検証する。

ファイル内容

5. バックエンド・DB との整合

項目要件
最大桁数フロント 50 / API リクエスト項目 / DB カラム長を同一にする
文字種API 側でもホワイトリスト検証を実施する（フロント検証は UX 目的であり、防御ではない）
保存方式パスワードは平文で保存・照合する（少人数・クローズド環境での利用を前提とするため、ハッシュ化は行わない）
注意点将来、利用者数の増加や外部公開を行う場合は、ハッシュ化（bcrypt / Argon2 等）への移行を再検討する
現状の扱い

mockUsers.ts の平文パスワード（pass1234）をそのまま踏襲し、DB 側でも平文で保持する。ただし、パスワードをログに出力したり localStorage に保存したりしないこと（4.3 No.4）。

6. パスワード強度ルール（参考・本画面の対象外）

新規登録・パスワード変更画面では、以下を適用することを想定する（本仕様では検査しない）。

  • 8 文字以上 50 文字以内
  • 英大文字・英小文字・数字・記号のうち 3 種類以上
  • ユーザーID と同一文字列の禁止
