1.現状の確認結果（設計に影響する点）

項目 api_kadou の現状 影響
CORS allow_origins=["http://localhost:5173"] のみ react-kadou（CRA は通常 3000）からは必ず CORS エラーになる
ルート /api/v1/user のみ 稼働管理用 API は未定義。パス設計が必要
エラー形式 FastAPI 既定の {"detail": ...}、422 は detail: [{loc,msg,type}]、500 は非 JSON の可能性 フロントで3 種類の形を正規化する必要がある
例外ハンドラ なし HTTPException 以外は 500 で詳細不明
Request ID なし 問い合わせ時の突合ができない
認証 なし（User は name/age のみ） ログイン・401・権限の扱いが未定
DB セッション finally: db.close() のみ IntegrityError 等を明示的に rollback しないと 500 になる
ポート 8000 react-kadou に proxy が無いため接続先設定が必要
レスポンス 生モデル（エンベロープ無し） react-ud の {code,msg,data} とは異なる

2.エラー契約（react-kadou が依存する前提）

2.1 エラー時のボディ（提案）

{
  "code": "KADOU_PERIOD_OVERLAP",
  "message": "有効期間が重複しています。",
  "detail": "developer-only detail",
  "fieldErrors": { "activeFrom": "開始週が不正です" },
  "requestId": "0f9c...",
  "timestamp": "2026-10-23T10:00:00+09:00"
}
  • 成功時：HTTP 2xx ＋ 既存どおり生データ（FastAPI らしさを維持）。
  • エラー時：HTTP 4xx/5xx ＋ 上記ボディ。
  • detail は APP_ENV=dev のみ返す（本番はログのみ）。

2.2 HTTP ステータスと code の対応（案）

HTTP 発生源 code 例 react-kadou の分類
400 業務チェック KADOU_BAD_REQUEST business
401 認証切れ AUTH_REQUIRED / AUTH_TOKEN_EXPIRED auth
403 権限不足 AUTH_FORBIDDEN forbidden
404 対象なし KADOU_NOT_FOUND notFound
409 重複・競合・参照中 KADOU_CONFLICT / KADOU_REFERENCE_IN_USE conflict / business
422 Pydantic 検証 VALIDATION_ERROR validation
429 レート制限（導入時） RATE_LIMITED rateLimit
500 想定外 SYSTEM_ERROR server
503 メンテナンス MAINTENANCE maintenance

3.api_kadou 側に必要な実装（前提条件）

app/core/errors.py # ErrorCode / AppError app/core/exception_handlers.py # 例外 → 2.1 の形に変換 app/middleware/request_id.py # X-Request-Id 受理・採番・返却

ハンドラで必ず変換する対象

  1. RequestValidationError → 422 / VALIDATION_ERROR / fieldErrors（loc から項目名を生成）
  2. AppError（独自）→ 指定ステータス・code
  3. HTTPException → ステータスに応じた code（detail が文字列なら message に）
  4. IntegrityError → db.rollback() 後、重複キーは 409、FK 違反は 409 KADOU_REFERENCE_IN_USE
  5. その他 Exception → 500 SYSTEM_ERROR（ログに stack、レスポンスには出さない）
  6. 500 でも JSON を返す（フロントの badResponse を避ける）
補足：現状の get_db() は finally: db.close() のみです。 例外時に明示的な rollback() を入れるか、例外ハンドラ側で必ず rollback する設計にしてください。

4.react-kadou 側の設計

4.1 追加ファイル

src/api/ config.ts # baseURL(/api/v1)・timeout・mock 切替 http.ts # axios・X-Request-Id・retry normalizeError.ts # FastAPI 3形式 → ApiError ApiError.ts # 型 errorMessages.ts # code → 日本語文言 notify.ts # 重複トースト抑止 auth.ts # token 保持・401 イベント kadouApi.ts # エンドポイント src/data/ httpKadouRepository.ts src/hooks/ useApiAction.ts src/components/ BootErrorScreen.tsx SaveErrorBanner.tsx setupProxy.js

4.2 FastAPI 固有の正規化（normalizeError.ts）

受信内容 判定
data.code あり code → 辞書 → ApiError
data.detail が文字列 message = detail（detail 欠落時は既定文言）
data.detail が配列（422） fieldErrors を loc の末尾キーで構築、kind=validation
ボディが HTML / 文字列 / 空（500） kind=badResponse、requestId はヘッダから
ERR_NETWORK navigator.onLine で offline / それ以外は network
ECONNABORTED timeout
axios cancel canceled（UI 非表示）
CORS とサーバー停止の区別： ERR_NETWORK かつオンラインの場合、GET /api/health を 3 秒で 1 回だけ試行します。 成功 →「通信経路の設定エラー（管理者へ連絡）」／失敗 →「サーバーに接続できません」。

4.3 接続方式

setupProxy.js で /api → http://localhost:8000 に転送し、 baseURL は空（同一オリジン）にします。 CORS 設定変更に依存せず、環境差分も吸収できます。

4.4 リトライ・タイムアウト

操作 timeout 自動 retry
ログイン10sなし
年度データ取得10s2回（GET、500/502/503/504/timeout）
マスタ保存15sなし
稼働表保存30sなし（Idempotency-Key）
一括取込60sなし
統計30s2回
  • 401/403/404/409/422 は retry しない。
  • 保存は unmount しても中断しない。

4.5 起動時

App.tsx の同期 snapshot() を廃止し、loading / ready / error の状態機械に変更します。

  • error では BootErrorScreen（再試行／ログインへ／メンテナンス表示）。
  • 年度切替の取得失敗は現在年度を維持し、トースト＋再試行。

4.6 保存系

保存 失敗時の挙動
稼働表 dirty を維持、SaveErrorBanner＋再試行。成功時のみ成功トースト
マスタ 楽観更新を維持。年度単位の直列キューで順序保証。失敗時は巻き戻さず「未保存」バナー＋再試行
一括取込 部分成功を許容（成功件数＋失敗明細）。KADOU_IMPORT_PARTIAL は警告扱い

4.7 認証

401（セッション切れ）

トークン破棄 → 再ログイン誘導。稼働表の下書きは sessionStorage に退避し、復帰後に復元提案。

403（権限不足）

画面遷移させず、操作不可の理由を表示。

複数タブ

別タブのログアウトは storage イベントで検知。

ログイン失敗

認証失敗と通信不可を区別して表示。

8.疑問点・確認事項（独断しないため確認）

  1. API 契約：/api/v1/kadou/years/{year} などのパス・ペイロードは既に決まっていますか。未確定なら、react-kadou の YearStore（departments/personnel/projects/holidays/workStatus）をそのまま返す想定でよいですか。
  2. レスポンス形式：成功は生データ＋HTTP ステータス（FastAPI 標準）でよいですか。それとも react-ud と同じ {code,msg,data} 形式に統一しますか。
  3. エラー文言の所有者：message をバックエンドが日本語で返しますか。それともフロントが code から日本語辞書で表示しますか。
  4. CORS / proxy：CORS に http://localhost:3000 を追加しますか。それとも setupProxy.js で /api を 8000 に転送しますか。
  5. 認証方式：JWT ですか。有効期限・リフレッシュ API はありますか（現状 User にパスワード項目が無い）。
  6. 認可：部長／事業部長／管理者の権限チェックはバックエンドで行いますか。403 の返却単位は API 全体か項目単位か。
  7. 422 の項目名：fieldErrors のキーは英語（employeeNo）でよいですか。それとも日本語ラベルを返しますか。
  8. 競合制御：updated_at / version による楽観ロックは導入しますか。409 を返す想定はありますか。
  9. 冪等性：Idempotency-Key を受け付ける実装は可能ですか（稼働表保存の二重登録防止）。
  10. 一括取込：クライアントで解析して JSON 一括 POST ですか。それともファイルアップロードですか。部分成功のレスポンス形式は決まっていますか（200＋明細 / 207）。
  11. エラー詳細：本番で detail（SQL 等）を返さない前提でよいですか。
  12. Request ID / ログ：X-Request-Id を採用し、バックエンドでログ出力しますか。出力先（ファイル／標準出力）は。
  13. メンテナンス：503 の専用文言・再試行不可の扱いは必要ですか。
  14. ヘルスチェック：/api/health をフロントの疎通判定に使ってよいですか（CORS とサーバー停止の切り分け）。
  15. タイムアウト値：上記（10/15/30/60 秒）で問題ないですか。
