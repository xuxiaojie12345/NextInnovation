1. 基本方針

  • 年度を最上位キーとする
  • 部門・要員・プロジェクト・休日は年度ごとに凍結
  • 要員の同一性は employeeNo
  • マスタは即時保存、稼働表は明示保存
  • 稼働表では社員番号を入力できる
  • 氏名・役割・所属は要員マスタから表示し、稼働表では編集不可（所属は行が保持し、異動でのみ変わる）
  • 要員マスタの追加・削除と氏名・役割の更新は要員情報画面で行う
  • 要員の所属（departmentId）を更新できるのは「新規登録」「一括取込」「異動」だけ。要員情報画面の更新では変更できない
  • 部門の削除は、同一性年度の要員・プロジェクト・稼働表行から参照されていない場合のみ許可する（ユーザーの所属はチェックしない）
  • 部門IDは再利用しない（年度ごとの採番カウンタを保持する）
  • 済南稼働統計は画面初期時に年度データから計算（保存しない。教育実施人数も実データから算出）。対象部門は部門マスタから動的生成する
  • ユーザーの所属部門は年度ごとに保持。所属部門が削除済みの場合は「全部門」として扱う
  • 所属が未設定（空欄）の要員は、要員情報の保存・稼働表の保存・異動を拒否する
  • 一括読み込みの重複時は「上書き」か「中止」をユーザーが選択
  • 部門の一意制約は (year, departmentId)（部門名の一意制約はなし）
  • プロジェクトの一意制約は (year, customer, caseName, team, subTeam)（現場の運用に合わせる）
  • プロジェクトは「有効flg」「教育flg」の 2 つの独立した真偽値を持つ（同時に true 可。有効期間は持たない）
  • 既定値は 有効flg = true / 教育flg = false（新規登録・一括取込・既存データの補完すべて同じ）
  • 2 つのフラグは統計の集計だけに作用し、割当・BUFFER・選択肢・件数には影響しない

2. 全体構成

type Year = number;
type WeekKey = string;      // 月曜 'YYYY-MM-DD'
type DepartmentId = string;
type ProjectId = string;
type EmployeeNo = string;

interface YearData {
  year: Year;
  departments: Department[];
  personnel: Personnel[];
  projects: Project[];
  holidays: Holiday[];
  workStatus: WorkStatusData;
  userDepartments: UserDepartment[];
}

App は Record<Year, YearData> を保持し、選択中の年度の YearData を各画面へ渡します。

3. エンティティ定義

3.1 部門

interface Department {
  departmentId: DepartmentId;
  name: string;
  location: '天津' | '済南';
  kind: 'dept' | 'partner';
}
  • 主キー：(year, departmentId)
  • 一意制約：(year, departmentId)
  • 部門名の一意制約は設けない（同一年度内で同名可）
  • 参照はすべて departmentId
  • 部門IDは年度内で採番し、削除後も再利用しない（年度ごとの採番カウンタを保持する）
  • 名称・拠点・種別は随時変更できる（参照はIDのため、名称変更は参照側に影響しない）
  • 削除できるのは、同一年度の要員・プロジェクト・稼働表行のいずれからも参照されていない場合のみ（ユーザー年度別所属はチェックしない）

3.2 要員

interface Personnel {
  employeeNo: EmployeeNo;      // 同一性・主キー
  name: string;
  departmentId: DepartmentId;
  role: string;
  leavePlan?: string;
}
  • 主キー：(year, employeeNo)
  • 画面の rowKey も employeeNo
  • Personnel.id のような行IDは保存データには持たせない
  • departmentId は新規登録時に必須（既定値は置かない）
  • departmentId を更新できるのは新規登録・一括取込・異動（稼働表の保存成功時）だけ。要員情報画面の更新では変更しない
  • 異動後は「現在の所属」として異動後の部門を持つ（異動履歴は稼働表行が保持する）

3.3 プロジェクト

interface Project {
  projectId: ProjectId;     // システム項目ID（主キー・システム採番）
  customer: string;         // 顧客（必須）
  caseName: string;         // 案件（必須）
  team: string;             // チーム（任意）
  subTeam: string;          // Subチーム（任意）
  departmentId: DepartmentId;
  name: string;
  projectCode: string;      // 画面の「項目ID」（任意・重複可）
  validFlg: boolean;        // 有効flg（既定 true。統計の稼動系指標に作用）
  educationFlg: boolean;    // 教育flg（既定 false。統計の教育実施人数に作用）
  // abbr は派生値のため保存しない
}
  • 主キー：(year, projectId)
  • 一意制約：(year, customer, caseName, team, subTeam)
  • 取込時の重複判定：(year, customer, caseName, team, subTeam)
  • 比較時は前後空白のみ除去する。全角/半角・大文字/小文字は区別する
  • projectCode（画面の「項目ID」）は任意・重複可。一意判定には使わない
  • チーム・Subチームは任意のため、空欄も 1 つの値として扱う（空欄同士は同一とみなす）
  • 所属部門（departmentId）は一意判定に含めない
  • 手動登録で同じキーが既にある場合はエラーで拒否する（上書きはしない）
  • abbr は「顧客の1文字目＋案件＋チーム＋Subチーム」から都度生成
  • validFlg / educationFlg は主キー・一意制約・重複判定に含めない
  • 「無効」は validFlg = false の別名で、独立した状態フィールドは持たない
  • フラグに有効期間は持たせない（統計は常に現在のマスタ値で計算するため、変更は過去週にも及ぶ）
  • フラグを変更しても、既存の割当・BUFFER は変更しない（運用で整合を保つ）
顧客・案件は必須、チーム・Subチームは任意です。そのため 「顧客・案件は同じで、チーム・Subチームがどちらも空欄」の 2 行は同一プロジェクトと判定されます。
空欄と - や なし のような文字列は別の値として扱います。
所属部門が異なっていても、顧客・案件・チーム・Subチームが一致すれば同一プロジェクト（重複）です。

有効flg・教育flg の組み合わせ

validFlgeducationFlg意味稼動系指標教育実施人数
truefalse通常の有効プロジェクト計上する計上しない
truetrue有効な教育プロジェクト計上する計上する（重複計上）
falsefalse無効計上しない計上しない
falsetrue無効な教育プロジェクト計上しない計上する
2 つのフラグに優劣・排他はありません。教育flg は有効flg と無関係に判定します。 有効flg は「稼動」にだけ、教育flg は「教育実施人数」にだけ作用します。

3.4 休日

interface Holiday {
  holidayId: string;
  date: string;    // 'YYYY-MM-DD'
  name: string;
  kind: '祝日' | '会社休日' | '振替休日';
}
  • 主キー：(year, holidayId)
  • 一意制約：(year, date)

3.5 稼働データ

interface WorkStatusData {
  /** 稼働表に表示する行（並び順） */
  rows: WorkStatusRow[];
  /** 要員×週の割当（projectId / null = 明示的な未割当） */
  assignment: AssignmentMap;
  /** 要員×週の BUFFER（無償支援） */
  unpaid: UnpaidMap;
}

interface WorkStatusRow {
  key: string;                 // 行キー（異動で分割された行を区別する）
  employeeNo: EmployeeNo;      // 業務上の同一性キー
  departmentId: DepartmentId;  // この行の所属
  activeFrom?: WeekKey;        // 未指定 = 年度初め
  activeTo?: WeekKey;          // 未指定 = 年度末
  employeeNoLocked?: boolean;  // 異動で分割された行（社員番号は 2 行まとめて変更する）
  splitFromKey?: string;       // 異動元の行キー
}

/** 要員ID -> (週キー -> プロジェクトID または null) */
type AssignmentMap = Record<
  EmployeeNo,
  Record<WeekKey, ProjectId | null>
>;

/** 要員ID -> (週キー -> true = BUFFER) */
type UnpaidMap = Record<EmployeeNo, Record<WeekKey, boolean>>;
  • 稼働表行：(year, key)。employeeNo は年度内で最大 2 行（異動 1 回・有効期間は重ならない）
  • 割当：(year, employeeNo, weekKey)
  • 1人要員・1週につき1プロジェクト（＋BUFFERフラグ）

3.6 ユーザー年度別所属

interface UserDepartment {
  userId: string;
  year: Year;
  departmentId?: DepartmentId; // undefined = 全部門
}
  • 主キー：(year, userId)
  • 未設定年度は「全部門表示」

4. 主キー・一意制約一覧

データ主キー一意制約・重複判定
部門(year, departmentId)(year, departmentId)。IDは削除後も再利用しない
要員(year, employeeNo)(year, employeeNo)
プロジェクト(year, projectId)(year, customer, caseName, team, subTeam)
休日(year, holidayId)(year, date)
稼働表行(year, key)employeeNo は年度内で最大 2 行（異動 1 回）。同じ社員の行は有効期間が重ならない。異動で分割された行は保存後に削除できない
割当(year, employeeNo, weekKey)(year, employeeNo, weekKey)
ユーザー所属(year, userId)(year, userId)

割当の一意制約の目的

  • 同じ要員・同じ週の二重登録を防ぐ
  • 稼働人数・稼働率の二重計上を防ぐ
  • 稼働表の「要員 × 週」セルを一意に特定する
  • 保存時の登録／更新判定を明確にする
  • projectId = null を「明示的な未割当」として扱えるようにする
将来、1週間に複数プロジェクトへ工数配分する場合は、(year, employeeNo, weekKey) では足りません。 その場合は projectId や割当行ID、工数比率を追加してキーを見直す必要があります。

6. 画面ごとの責務と保存

画面できること保存
部門管理部門の追加・更新・削除（削除は要員・プロジェクト・稼働表行から参照されていない場合のみ）即時保存
要員情報要員マスタの追加・削除・氏名／役割の更新・一括取込（所属は新規登録時のみ選択）即時保存
プロジェクト管理プロジェクトの追加・更新・削除・一括取込、有効稼働・教育かどうかの設定即時保存
休日設置休日の追加・更新・削除・一括取込即時保存
要員稼動管理行追加・行削除、社員番号入力、所属変更（異動）、割当、BUFFER（過去年度は参照のみ）明示保存
済南稼働率統計表示のみ（初期時に計算）保存しない
ユーザー管理ユーザー・年度別所属の管理（所属部門が削除済みの場合は保存時にクリアして全部門）即時保存

6.1 プロジェクト管理のフラグ UI

  • 登録・修正フォームに「有効稼働」「教育かどうか」のチェックボックスを置く（新規時は 有効 = ON、教育 = OFF）
  • 一覧に「有効稼働」「教育かどうか」列を追加する（列幅の目安：110 / 150）
  • セルの表示は文字のみ（有効 / 無効、教育 / 非教育）。チェックボックスは置かず、入力はフォームで行う
  • 一覧の列ヘッダーフィルタで「有効 / 無効」「教育 / 非教育」を単一選択で絞り込める（表示だけに作用し、データは変えない）
  • 年度を切り替えたときは絞り込みを解除する
  • 無効プロジェクトも要員稼動管理の週セルの選択肢・列フィルタの候補に残す（有効・無効は統計上の扱いだけ）

7. 要員稼動管理の詳細

7.1 行追加

  • 稼働表に空行を追加する
  • ユーザーが社員番号を入力する
  • 入力確定時に要員マスタを検索する
  • マスタに存在すれば、氏名・役割・所属を表示する
  • マスタに存在しなければエラーを表示し、行は確定しない
  • 新規要員は、先に要員情報画面でマスタ登録する

7.2 社員番号の入力

  • 稼働表の社員番号欄は入力可能
  • 入力確定（Enter / フォーカスアウト）時に要員マスタを検索
  • 一致する employeeNo がある場合のみ行を確定
  • 同じ employeeNo が既に rows にある場合はエラー（異動による 2 行のみ、有効期間が重ならない場合に許可）
  • 社員番号の入力によって要員マスタを新規作成・更新しない
  • 氏名・役割・所属はマスタから自動表示し、稼働表では編集不可（所属は行が保持する値を表示する）

7.3 マスタ項目

稼働表での扱いは次のとおりです。

項目稼働表での扱い
社員番号入力可（行の識別子）
氏名表示のみ
役割表示のみ
所属表示のみ

氏名・役割の変更は要員情報画面で行います。所属の変更は稼働表の「異動」だけで行い、要員情報画面では変更できません。稼働表の「所属」列は行が保持する所属を表示するため、要員マスタの現在所属を変更しても、既存の行（過去の異動履歴）の所属は変わりません。

7.4 過去実績の保護（共通ルール）

  • 過去実績＝当年度の「年度初め〜先週の日曜日」の週に、次のいずれかがあること
    • プロジェクトの割当（projectId が非 null。退職「内・退職」を含む）
    • BUFFER（無償支援）
  • 判定は保存済みデータで行う（画面を開いた時点の内容。保存成功時にその payload で判定基準を更新する）
  • 過去実績の判定範囲は操作によって異なる
    • 行削除：対象行の有効期間 ∩ 過去
    • 社員番号変更：同じ社員の全行（1〜2 行）の有効期間 ∩ 過去（2 行まとめて変更するため）
  • 過去実績がある場合は行削除・社員番号変更を禁止する（ボタン・入力欄を無効化し、ツールチップで理由を表示する）
  • 過去年度は全期間が過去、未来年度は過去なし（＝制限なし）
  • 過去週（今週の月曜より前）のセルは編集不可（読み取り専用）
    • セルには項目の略称を表示する（空白にしない）。グレー表示で、クリック・選択・プルダウンは不可
    • BUFFER の切替、貼り付け、矩形選択は不可。右クリックメニューは「コピー」のみ可（編集系メニューは不可）
    • 「内・退職」も今週以降からしか設定できない
  • 過去年度の稼働管理画面は参照のみ（行追加・行削除・異動・保存・退場予定の編集は不可）
  • 今週（今週の月曜〜日曜）は編集できる。行削除で消えるのは今週以降の分だけ（過去実績がある行はそもそも削除できない）
  • 画面を開いたまま週が変わった場合は、過去の範囲を再計算する
  • 行削除で行の所属や有効期間が変わると、済南稼働統計の過去の「人数」が変わることがある（人数は割当の有無に関係なく「行の所属 × 有効期間」で数えるため）。これは許容する

7.5 行削除

  • 削除できるのは、過去実績が無い行だけ（判定は 7.4 の行単位）
  • 削除前に警告（確認ダイアログ）を表示する
    • 残りの行がある場合（未保存の異動を取り消す場合）：「この行（社員番号・所属・期間）と、この行の期間の業務データ（割当・BUFFER）を削除します。要員マスタは削除されません。残りの行は期間が自動で延長されます。」
    • 最後の 1 行の場合：「この行と、当該年度の業務データ（割当・BUFFER）をすべて削除します。要員マスタは削除されません。」
    • キャンセルした場合は何も変更しない
  • 保存済みの異動で分割された行は削除できない（異動の取消は不可）。削除ボタンを無効化し、ツールチップで理由を表示する
    • 未保存（下書き）の異動は取り消せる。前段・後段のどちらかを削除すると、残った行が期間を吸収して 1 行に戻り、splitFromKey と employeeNoLocked を解除する
    • 保存済みかどうかは、保存済みデータ（サーバー／ストア）に行が存在するかで判定する
  • 業務データ（assignment / unpaid）は、削除する行の期間内だけ削除する
  • 要員マスタ（要員情報）は削除しない。稼働表の表示行から外すだけ
  • その社員の最後の行を削除した場合は、当該年度の業務データをすべて削除する
  • 削除後に同じ社員番号を再入力して行追加しても、業務データが無いため全ての週が「未割当」で表示される（過去の割当は復元しない）
  • 保存済みの異動は取り消せないため、行削除で 1 行に戻るのは未保存の異動だけである
  • 行削除は明示保存。未保存の異動を取り消す場合など、同じ社員の行が残る場合も対象社員を deletedEmployeeNos に含める。API は「削除 → payload 反映」の順で処理するため、残った行の実績は保持され、削除した期間の実績だけが消える（7.8 参照）

7.6 所属変更（異動）の上限

  • 1 人の社員が異動できるのは同一年度内で 1 回まで（＝行は最大 2 行）
  • 異動で 2 行になっている間は、両方の行の「異動」ボタンを無効化する
    • 無効化したボタンにはツールチップで「1年度につき異動は1回までです」と表示する
  • 適用開始週は今週の月曜以降とする（過去週には異動できない）
    • 過去年度は適用できる週が無いため、異動できない
  • 保存済みの異動は取り消せない（行削除を禁止）。そのため、保存した異動は年度内で確定し、同じ社員は再度異動できない
    • 未保存（下書き）の異動は行削除で取り消せる
  • 異動の確定時は、保存後に取り消せない旨を確認ダイアログで明示する
  • 保存（API）側でも、同一 employeeNo の行が 2 行を超える場合、適用開始週が今週の月曜より前の場合は保存を拒否する

7.7 社員番号の変更と割当

  • 過去実績が無い場合（7.4 の社員単位判定）、割当の有無に関係なく変更できる（入力ミスの訂正を含む）
  • 過去実績がある社員は、社員番号欄を編集できない（読み取り専用の表示＋ツールチップで理由を表示）
  • 異動中の 2 行も変更できる。この場合は2 行まとめて同じ社員番号に変更する（片方だけの変更は不可）
  • 変更すると、その社員の既存の割当・BUFFER は新しい社員番号へ引き継ぐ（行の表示は変わらない）
  • 旧社員番号の当年度の業務データは残さない（新しい社員番号へ移す）
  • 新しい社員番号に既存データがある場合は、引き継いだデータで上書きする
  • 保存時は旧社員番号を deletedEmployeeNos に含めて送る（バックエンドは旧番号のデータを削除してから、新番号のデータを反映する）
  • 社員番号を空にできるのは、次をすべて満たす場合だけ
    • 異動中の 2 行ではない（保存済みの異動は取り消せないため、2 行のままでは空にできない）
    • 当該社員の業務データ（割当・BUFFER）が下書き・保存済みのどちらにも無い
  • 空にできない場合はメッセージを表示し、入力前の社員番号に戻す

7.8 保存ペイロード

interface WorkStatusPayload {
  year: Year;
  rows: WorkStatusRow[];
  assignment: AssignmentMap;
  unpaid: UnpaidMap;
  /** 異動で変更した要員の現在所属（保存成功時に要員マスタへ反映する） */
  departmentUpdates: { employeeNo: EmployeeNo; departmentId: DepartmentId }[];
  /** 行削除・社員番号変更で業務データを削除した社員番号 */
  deletedEmployeeNos: EmployeeNo[];
}
  • personnel（氏名・役割など）は含めない。ただし異動による現在所属の更新だけは departmentUpdates として含める
  • departmentUpdates は稼働表の保存と同一トランザクションで要員マスタへ反映する（保存失敗時は反映しない。未保存の異動では現在所属を変更しない）
  • deletedEmployeeNos の要員は、当該年度の割当・BUFFER を削除してから assignment / unpaid を反映する
  • deletedEmployeeNos は「最後の行を削除した場合」だけでなく、「未保存の異動を取り消すなどして一部の行を削除した場合」も対象社員を含める（削除→反映の順のため、残った行の実績は保持される）
  • deletedEmployeeNos に無い要員の割当は削除しない（画面に表示していないだけの実績を守る）
  • 社員番号が空の行がある場合は保存不可
  • 未保存フラグは稼働表のみ対象

7.9 要員マスタ削除時

  • 割当の有無では削除をブロックしない（要員マスタは削除できる）
  • 削除すると、選択中の年度の稼働データ（稼働表行・割当・BUFFER）も同時に削除する（カスケード）
    • 過去実績も削除対象（7.4 の過去実績保護の例外）
    • 他の年度のデータは削除しない
  • 当年度に稼働データ（稼働表行・割当・BUFFER）がある場合のみ、削除前に確認メッセージを表示する
    • 「当年度の稼働表行・割当・BUFFERも削除されますが、よろしいでしょうか。」
    • 稼働データが無い場合は確認なしで削除する
  • 異動で 2 行になっている要員でも、要員マスタ削除は可能（行の削除禁止は「行削除」操作に対する制約で、要員マスタ削除のカスケードには適用しない）
  • 削除は即時保存（要員情報画面）

8. 一括読み込み

8.1 共通フロー

  1. ファイルを解析
  2. 必須項目・形式を検証
  3. ファイル内の重複を検出
  4. ファイル内重複があればエラーで中止
  5. 既存データとの重複を検出
  6. 重複がなければ、そのまま追加
  7. 重複があれば、ダイアログで選択
重複が N 件あります
[重複を上書きして取り込む] [中止]
  • 中止：ファイル全体を中止し、1件も反映しない
  • 上書き：重複分は更新、新規分は追加
  • 結果は「追加 N 件 / 上書き M 件 / スキップ K 件 / 警告」で返す

8.2 重複キー

マスタ重複キー
要員(year, employeeNo)
プロジェクト(year, customer, caseName, team, subTeam)
休日(year, date)

8.3 プロジェクト取込のルール

  • 重複キーは (顧客, 案件, チーム, Subチーム)。ファイル内・既存データの両方でこのキーを使う
  • 顧客・案件は必須。空欄の行が 1 行でもあればファイル全体を中止する
  • ファイル内で同じ重複キーが複数ある場合もファイル全体を中止する
  • 既存データと重複した場合は「上書き」か「中止」を選択
  • projectCode（項目ID）は任意。空欄・重複とも可
  • 取込ファイルに「有効稼働」「教育かどうか」の列は存在しない前提。列があっても読み取らない
  • 新規追加分のフラグは既定値（validFlg=true / educationFlg=false）にする
  • 上書き時は 所属部門・Project名称・項目ID を新しい値で更新し、projectId は維持する
  • 上書き時のフラグは既存値を維持する（既定値に戻さない）
  • 比較時は前後空白のみ除去し、全角/半角・大文字/小文字は区別する
  • チーム・Subチームの空欄は空文字として比較する（- や なし とは別の値）

8.4 検証エラー

  • 必須項目不足などは行単位で警告し、その行は取り込まない
  • 重複エラーはファイル全体の中止対象
  • ただしプロジェクト取込では、顧客・案件の空欄とファイル内重複はファイル全体の中止対象
  • 取込後の結果に、警告内容と行番号を含める

8.5 要員取込の部門ルール

  • 要員の一括取込は「所属を変更できる公式な例外」とする（要員情報画面の更新では所属を変更できない）
  • 新規社員：所属（部門名）は必須。空欄、部門マスタに存在しない、同名部門が複数で一意に決められない場合はエラーとし、その行は取り込まない
  • 既存社員：氏名・役割・所属を上書きする（所属もファイルの値で更新する）
  • 所属列が空欄の既存社員は、現在の所属を保持する
  • 新規社員の所属は、部門マスタに存在する部門IDに解決できた場合のみ登録する

9.2 指標

  • 総人数
  • 離職人数
  • 総稼動人数
  • 総稼動率
  • 非契約稼動人数
  • 教育実施人数

9.3 指標の定義と集計ルール

指標定義
総人数その週の部門の有効行数 − 離職人数
離職人数その週に「内・退職」が設定されている人数（退職後は毎週計上。総人数からは除外）
総稼動人数割当あり かつ 有効稼働flg = true の人数（BUFFER を含む）
総稼動率総稼動人数 ÷ 総人数 × 100
非契約稼動人数有効稼働flg = true かつ BUFFER の人数（無効プロジェクトの BUFFER は含めない）
教育実施人数割当あり かつ 教育flg = true の人数（有効/無効・BUFFER と無関係）
現地稼動人数（日本出張含）総稼動人数
現地稼動率現地稼動人数 ÷ 総人数 × 100（= 総稼動率）
契約稼働率（総稼動人数 − 非契約稼動人数）÷ 総人数 × 100
  • 率は小数第 1 位で四捨五入する。分母が 0 のときは 0% とする
  • 総人数 + 離職人数 = その週の部門の有効行数
  • 済南全社は対象部門の合計（率は合計値から計算する）

1 人 × 1 週の判定は、次の前提の上で行います。

  • 行がその週の有効期間内、統計対象の departmentId、かつ「内・退職」でないこと
  • その週の割当（assignment）の projectId からプロジェクトを引き、フラグを判定する
指標計上条件
総稼動人数割当あり かつ validFlg = true（BUFFER を含む）
非契約稼動人数総稼動人数の条件を満たし、かつ BUFFER
教育実施人数割当あり かつ educationFlg = true（validFlg は問わない。BUFFER でも計上）
  • 無効プロジェクトの割当は、稼動系指標（総稼動人数・総稼動率・非契約稼動人数・現地稼動人数・現地稼動率・契約稼動率）に計上しない（「未割当」という指標は設けない）
  • 有効かつ教育のプロジェクトは、総稼動人数と教育実施人数の両方に計上する（重複計上を許容）
  • 無効かつ教育のプロジェクトは、教育実施人数にのみ計上する
  • 「内・退職」は名称で判定し、フラグ判定より先に除外する（フラグの値は使わない）
  • フラグは保存時点のスナップショットではなく現在のプロジェクトマスタ値を使うため、後から変更すると過去週の値も変わる
  • フラグを変更しても割当・BUFFER は変更しない
教育実施人数は 2026-10 以降、プロジェクトマスタの教育flg から算出します（従来のモック値を廃止）。

12. バリデーション

  • 部門ID：同一年度内で一意
  • 部門IDは削除後も再利用しない（年度ごとの採番カウンタ）
  • 部門削除時は、同一年度の要員・プロジェクト・稼働表行からの参照をチェックし、参照があれば削除を拒否する（ユーザー年度別所属はチェックしない）
  • 部門名：一意制約なし（同名可）
  • 社員番号：同一年度内で一意
  • プロジェクト：(顧客, 案件, チーム, Subチーム) が同一年度内で一意
  • プロジェクトの projectCode（項目ID）は一意制約なし（重複可）
  • プロジェクトの validFlg / educationFlg は必須の真偽値（null・未設定は不可。既存データは既定値で補完する）
  • 2 つのフラグの組み合わせは検証しない（同時 true・無効 + 教育をいずれも許可する）
  • 休日：同一年度内で日付一意
  • 要員の departmentId は存在する部門IDを参照。新規登録時は必須（空欄不可）
  • 要員の departmentId は、要員情報画面の更新では変更できない（新規登録・一括取込・異動のみ）
  • 稼働表の保存で要員の現在所属を変更できるのは、異動（departmentUpdates）だけ
  • 保存済みの異動で分割された行の削除を拒否する（未保存の異動の取消は許可）
  • departmentId が空の要員が含まれる場合、要員情報の保存・稼働表の保存・異動を拒否する
  • プロジェクトの departmentId は存在する部門IDを参照
  • 割当の projectId は存在するプロジェクトIDを参照
  • 稼働表の rows は要員マスタに存在する employeeNo のみ
  • 稼働表の rows 内で employeeNo は重複不可（異動による 2 行のみ、有効期間が重ならない場合に許可）
  • 同一 employeeNo の行は 1 年度につき最大 2 行（3 行以上になる保存は拒否）
  • 過去週（年度初め〜先週の日曜）の assignment / unpaid が保存済みデータと異なる場合は保存を拒否
  • 過去実績がある行の削除、および過去実績がある社員の社員番号変更を含む保存は拒否
  • 異動（同一社員の 2 行）の適用開始週が今週の月曜より前の場合は保存を拒否
  • 社員番号が空の行がある場合は保存不可
  • 週キーは対象年度の週リスト内に存在
  • 要員マスタ削除時は参照チェックを行わない（当年度の稼働データも同時に削除する。異動済みの行も削除対象）

部門名が重複可能になるため、部門選択肢は必要に応じて「部門名（部門ID）」のように区別できる表示にします。

過去年度稼働管理画面は参照のみ（行追加・行削除・異動・保存・退場予定の編集は不可）
異動の適用開始週今週の月曜以降のみ。過去年度は異動できない
一部の行を削除した場合未保存の異動の取消などで同じ社員の行が残っても deletedEmployeeNos に含める（削除→反映の順で残った行の実績は保持）
要員マスタ削除ブロックしない。選択年度の稼働表行・割当・BUFFER も削除（過去実績含む）。稼働データがある場合のみ確認メッセージを表示。他年度は削除しない

14.3 確定した事項（有効flg・教育flg）

論点確定内容
教育と有効の関係無関係。教育プロジェクトが有効・無効のどちらにもなり得る。同時に true も可
無効の扱い有効でないプロジェクトはすべて無効（「無効」は validFlg=false の別名で、独立した状態は持たない）
既定値新規登録・一括取込とも 有効flg = true / 教育flg = false
既存データ同じ既定値（true / false）で補完する
取込ファイル有効・教育の列は存在しない前提。列があっても読み取らず、既定値を使う
取込の上書き時フラグは既存値を維持する（新規追加分だけ既定値を適用）
無効プロジェクトの選択要員稼動管理の週セルで選択できる（有効・無効は統計上の扱いだけ）
フラグ変更時の連動既存の割当・BUFFER は変更しない
無効の割当と稼動指標総稼動人数・稼動率に計上しない（未割当という指標は設けない）
教育の割当と稼動指標稼動系の計上は有効flg だけで決める。教育flg は稼動判定に影響しない（有効 + 教育は両方に計上）
無効 + 教育教育実施人数に計上する（教育flg は有効flg と無関係）
過去週の扱い現在のマスタ値で再計算する（過去週の値も変わることを許容）
年度選択カードの項目件数主データ全件（無効を含む）。フラグで変化しない
画面表示一覧は「有効稼働」「教育かどうか」を文字のみ（有効/無効、教育/非教育）で表示し、両方の条件で絞り込める。フォームはチェックボックス
取込の上書き時にフラグを既存維持とする扱いで記載しています。 現行の取込は重複可の追加のみで、将来「上書き」を実装する場合の前提です。

14.4 確定した事項（部門の更新・削除）

論点確定内容
部門の削除条件同一年度の要員・プロジェクト・稼働表行（異動の旧行を含む）のいずれからも参照されていないこと。ユーザー年度別所属はチェックしない
部門削除後のユーザー所属部門が存在しなければ「全部門」として扱う。ユーザー管理画面で編集保存するときに departmentId をクリアする
部門IDの採番削除後も再利用しない（年度ごとの採番カウンタを保持）
要員の所属の更新経路新規登録・一括取込・異動のみ。要員情報画面の更新（氏名・役割）では変更しない
要員情報画面の新規登録所属は必須（既定値なし）。更新時は氏名・役割のみ
異動の場所稼働表のみ。異動で行が 2 行になることは許容する
異動後の要員情報異動後の所属を表示し、編集できない
異動のマスタ反映稼働表の保存成功時に、同一トランザクションで要員の現在所属を更新する
将来週の異動保存成功した時点で新しい所属を表示する（適用週の到来を待たない）
異動の制約当年度・適用開始週は今週以降・年 1 回・対象社員に行が存在することを維持する。訂正手段は用意しない
保存済みの異動の取消禁止（分割行の削除をブロック）。未保存（下書き）の異動は取り消せる
一括取込の所属既存社員も所属を上書きする（公式な例外）。新規社員の所属が解決できない場合はエラー
空所属の要員部門を設定するまで、要員情報の保存・稼働表の保存・異動を拒否する
済南統計の対象部門部門マスタから動的生成（location='済南' かつ kind!='partner'）
プロジェクトの所属部門いつでも変更できる。統計はプロジェクトの所属部門を使わないため、変更は統計に影響しない
部長の可視範囲所属部門が削除された場合は全部門を閲覧できる状態を許容する（データ集約であり権限ではない）

14.5 残課題・要確認

  • 空所属の要員の修正手段：要員情報画面では所属を変更できず、異動もブロックされるため、修正は「一括取込」または「要員削除→再登録」だけになる。この運用でよいか
  • 要員マスタ削除のカスケード：異動済みの行も要員マスタ削除で消えるため、「保存済みの異動は取り消せない」に対する実質的な抜け道になる。許容するか
  • 取込エラーの粒度：所属が解決できない行を「行単位でスキップ」とするか「ファイル全体を中止」とするか（8.5 は行単位で記載）
  • 部門削除の実効性：稼働表行が参照している限り削除できないため、運用上はほとんど削除できない。この制約でよいか
  • 異動確定の確認ダイアログ：保存後に取り消せないことを明示する確認を出すか（7.6 に記載）
