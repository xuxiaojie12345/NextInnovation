1. 基本方針

  • 年度を最上位キーとする
  • 部門・要員・プロジェクト・休日は年度ごとに凍結
  • 要員の同一性は employeeNo
  • マスタは即時保存、稼働表は明示保存
  • 稼働表では社員番号を入力できる
  • 氏名・役割・所属は要員マスタから表示し、稼働表では編集不可
  • 要員マスタの追加・更新・削除は要員情報画面のみ
  • 済南稼働統計は画面初期時に年度データから計算（当面モック）
  • ユーザーの所属部門は年度ごとに保持
  • 一括読み込みの重複時は「上書き」か「中止」をユーザーが選択
  • 部門の一意制約は (year, departmentId)（部門名の一意制約はなし）
  • プロジェクトの一意制約は (year, customer, caseName, team, subTeam)（現場の運用に合わせる）

2. 全体構成

type Year = number;
type WeekKey = string;      // 月曜 'YYYY-MM-DD'
type DepartmentId = string;
type ProjectId = string;
type EmployeeNo = string;

interface YearData {
  year: Year;
  departments: Department[];
  personnel: Personnel[];
  projects: Project[];
  holidays: Holiday[];
  workStatus: WorkStatusData;
  userDepartments: UserDepartment[];
}

App は Record<Year, YearData> を保持し、選択中の年度の YearData を各画面へ渡します。

3. エンティティ定義

3.1 部門

interface Department {
  departmentId: DepartmentId;
  name: string;
  location: '天津' | '済南';
  kind: 'dept' | 'partner';
}
  • 主キー：(year, departmentId)
  • 一意制約：(year, departmentId)
  • 部門名の一意制約は設けない（同一年度内で同名可）
  • 参照はすべて departmentId

3.2 要員

interface Personnel {
  employeeNo: EmployeeNo;      // 同一性・主キー
  name: string;
  departmentId: DepartmentId;
  role: string;
  leavePlan?: string;
}
  • 主キー：(year, employeeNo)
  • 画面の rowKey も employeeNo
  • Personnel.id のような行IDは保存データには持たせない

3.3 プロジェクト

interface Project {
  projectId: ProjectId;     // システム項目ID（主キー・システム採番）
  customer: string;         // 顧客（必須）
  caseName: string;         // 案件（必須）
  team: string;             // チーム（任意）
  subTeam: string;          // Subチーム（任意）
  departmentId: DepartmentId;
  name: string;
  projectCode: string;      // 画面の「項目ID」（任意・重複可）
  // abbr は派生値のため保存しない
}
  • 主キー：(year, projectId)
  • 一意制約：(year, customer, caseName, team, subTeam)
  • 取込時の重複判定：(year, customer, caseName, team, subTeam)
  • 比較時は前後空白のみ除去する。全角/半角・大文字/小文字は区別する
  • projectCode（画面の「項目ID」）は任意・重複可。一意判定には使わない
  • チーム・Subチームは任意のため、空欄も 1 つの値として扱う（空欄同士は同一とみなす）
  • 所属部門（departmentId）は一意判定に含めない
  • 手動登録で同じキーが既にある場合はエラーで拒否する（上書きはしない）
  • abbr は「顧客の1文字目＋案件＋チーム＋Subチーム」から都度生成
顧客・案件は必須、チーム・Subチームは任意です。そのため 「顧客・案件は同じで、チーム・Subチームがどちらも空欄」の 2 行は同一プロジェクトと判定されます。
空欄と - や なし のような文字列は別の値として扱います。
所属部門が異なっていても、顧客・案件・チーム・Subチームが一致すれば同一プロジェクト（重複）です。

3.4 休日

interface Holiday {
  holidayId: string;
  date: string;    // 'YYYY-MM-DD'
  name: string;
  kind: '祝日' | '会社休日' | '振替休日';
}
  • 主キー：(year, holidayId)
  • 一意制約：(year, date)

3.5 稼働データ

interface WorkStatusData {
  /** 稼働表に表示する要員（並び順） */
  rows: EmployeeNo[];
  /** 要員×週の割当 */
  assignments: AssignmentMap;
}

interface AssignmentCell {
  projectId: ProjectId | null; // null = 未割当
  unpaid: boolean;             // BUFFER
}

type AssignmentMap = Record<
  EmployeeNo,
  Record<WeekKey, AssignmentCell>
>;
  • 稼働表行：(year, employeeNo)
  • 割当：(year, employeeNo, weekKey)
  • 1人要員・1週につき1プロジェクト（＋BUFFERフラグ）

3.6 ユーザー年度別所属

interface UserDepartment {
  userId: string;
  year: Year;
  departmentId?: DepartmentId; // undefined = 全部門
}
  • 主キー：(year, userId)
  • 未設定年度は「全部門表示」

4. 主キー・一意制約一覧

データ主キー一意制約・重複判定
部門(year, departmentId)(year, departmentId)
要員(year, employeeNo)(year, employeeNo)
プロジェクト(year, projectId)(year, customer, caseName, team, subTeam)
休日(year, holidayId)(year, date)
稼働表行(year, employeeNo)(year, employeeNo)
割当(year, employeeNo, weekKey)(year, employeeNo, weekKey)
ユーザー所属(year, userId)(year, userId)

割当の一意制約の目的

  • 同じ要員・同じ週の二重登録を防ぐ
  • 稼働人数・稼働率の二重計上を防ぐ
  • 稼働表の「要員 × 週」セルを一意に特定する
  • 保存時の登録／更新判定を明確にする
  • projectId = null を「明示的な未割当」として扱えるようにする
将来、1週間に複数プロジェクトへ工数配分する場合は、(year, employeeNo, weekKey) では足りません。 その場合は projectId や割当行ID、工数比率を追加してキーを見直す必要があります。

7. 要員稼動管理の詳細

7.1 行追加

  • 稼働表に空行を追加する
  • ユーザーが社員番号を入力する
  • 入力確定時に要員マスタを検索する
  • マスタに存在すれば、氏名・役割・所属を表示する
  • マスタに存在しなければエラーを表示し、行は確定しない
  • 新規要員は、先に要員情報画面でマスタ登録する

7.2 社員番号の入力

  • 稼働表の社員番号欄は入力可能
  • 入力確定（Enter / フォーカスアウト）時に要員マスタを検索
  • 一致する employeeNo がある場合のみ行を確定
  • 同じ employeeNo が既に rows にある場合はエラー
  • 社員番号の入力によって要員マスタを新規作成・更新しない
  • 氏名・役割・所属はマスタから自動表示し、稼働表では編集不可

7.3 マスタ項目

稼働表での扱いは次のとおりです。

項目稼働表での扱い
社員番号入力可（行の識別子）
氏名表示のみ
役割表示のみ
所属表示のみ

氏名・役割・所属の変更は要員情報画面でのみ行います。マスタが更新されると、稼働表の表示にも自動反映されます。

7.4 行削除

  • workStatus.rows から対象の employeeNo を外す
  • 要員マスタは削除しない
  • 過去の割当は保持する（表示対象から外れるだけ）
  • 同じ要員を再度行追加すると、過去の割当も再表示される
  • 割当自体を削除したい場合は、行削除とは別の操作にする

7.5 社員番号の変更と割当

  • 割当が無い行：社員番号の変更を許可する（入力ミスの訂正）
  • 割当がある行：社員番号の変更はブロックする
    • 行削除 → 行追加を案内する
    • 理由：割当は employeeNo をキーに保持しているため、社員番号を変えると過去の割当が新しい社員に移る／消える危険がある
  • どうしても変更を許可する場合は、確認ダイアログと「旧社員の割当を保持する／新社員は空にする」などの仕様が必要

7.6 保存ペイロード

interface WorkStatusPayload {
  year: Year;
  rows: EmployeeNo[];
  assignments: AssignmentMap;
}
  • personnel は含めない
  • rows に無い要員の割当は削除しない
  • 社員番号が空の行がある場合は保存不可
  • 未保存フラグは稼働表のみ対象

7.7 要員マスタ削除時

  • その年度の割当が存在する場合は削除をブロックする
  • または「割当も削除する」確認付きのカスケード削除
  • 推奨はブロック（誤削除防止）

8. 一括読み込み

8.1 共通フロー

  1. ファイルを解析
  2. 必須項目・形式を検証
  3. ファイル内の重複を検出
  4. ファイル内重複があればエラーで中止
  5. 既存データとの重複を検出
  6. 重複がなければ、そのまま追加
  7. 重複があれば、ダイアログで選択
重複が N 件あります
[重複を上書きして取り込む] [中止]
  • 中止：ファイル全体を中止し、1件も反映しない
  • 上書き：重複分は更新、新規分は追加
  • 結果は「追加 N 件 / 上書き M 件 / スキップ K 件 / 警告」で返す

8.2 重複キー

マスタ重複キー
要員(year, employeeNo)
プロジェクト(year, customer, caseName, team, subTeam)
休日(year, date)

8.3 プロジェクト取込のルール

  • 重複キーは (顧客, 案件, チーム, Subチーム)。ファイル内・既存データの両方でこのキーを使う
  • 顧客・案件は必須。空欄の行が 1 行でもあればファイル全体を中止する
  • ファイル内で同じ重複キーが複数ある場合もファイル全体を中止する
  • 既存データと重複した場合は「上書き」か「中止」を選択
  • projectCode（項目ID）は任意。空欄・重複とも可
  • 上書き時は 所属部門・Project名称・項目ID を新しい値で更新し、projectId は維持する
  • 比較時は前後空白のみ除去し、全角/半角・大文字/小文字は区別する
  • チーム・Subチームの空欄は空文字として比較する（- や なし とは別の値）

8.4 検証エラー

  • 必須項目不足などは行単位で警告し、その行は取り込まない
  • 重複エラーはファイル全体の中止対象
  • ただしプロジェクト取込では、顧客・案件の空欄とファイル内重複はファイル全体の中止対象
  • 取込後の結果に、警告内容と行番号を含める

9. 済南稼働統計

9.1 方針

  • 画面初期時に YearData から計算する
  • 当面はモック生成
  • 統計は保存しない
  • 年度データが変わったときだけ再計算する
const jinanStats = useMemo(
  () => calculateJinanWeeklyStats(yearData),
  [yearData],
);

9.2 指標

  • 総人数
  • 離職人数
  • 総稼動人数
  • 総稼動率
  • 非契約稼動人数
  • 教育実施人数
  • 現地稼動人数（日本出張含）
  • 現地稼動率
  • 契約稼動率

「天津出張人数」は削除済みです。現地稼動人数＝総稼動人数、現地稼動率＝総稼動率として扱います。

9.3 派生値

  • start / end は weekKey から生成
  • 部門名は departmentId から取得
  • 集計は departmentId 単位

9.4 将来

  • 勤怠・契約・教育・勤務地の実データが入ったら、同じセレクタで計算する
  • 過去年度の監査性が必要になった場合のみ、年度末に統計スナップショットを保存する

10. ユーザー年度別所属

  • UserDepartment を (year, userId) で保持
  • ユーザー管理画面は選択中の年度を受け取り、「YYYY年度の所属部門」として編集
  • defaultDepartmentsOf(user, year) は年度別所属を参照
  • 未設定年度は「全部門表示」
  • ログイン時は当年の所属を参照し、無ければ全部門表示

12. バリデーション

  • 部門ID：同一年度内で一意
  • 部門名：一意制約なし（同名可）
  • 社員番号：同一年度内で一意
  • プロジェクト：(顧客, 案件, チーム, Subチーム) が同一年度内で一意
  • プロジェクトの projectCode（項目ID）は一意制約なし（重複可）
  • 休日：同一年度内で日付一意
  • 要員の departmentId は存在する部門IDを参照
  • プロジェクトの departmentId は存在する部門IDを参照
  • 割当の projectId は存在するプロジェクトIDを参照
  • 稼働表の rows は要員マスタに存在する employeeNo のみ
  • 稼働表の rows 内で employeeNo は重複不可
  • 社員番号が空の行がある場合は保存不可
  • 週キーは対象年度の週リスト内に存在
  • マスタ削除時は参照チェックを行う

部門名が重複可能になるため、部門選択肢は必要に応じて「部門名（部門ID）」のように区別できる表示にします。

14. 決定事項と確認ポイント

14.1 確定した事項（プロジェクトの重複判定）

論点確定内容
重複キー(year, customer, caseName, team, subTeam)
正規化前後空白のみ除去。全角/半角・大文字/小文字は区別する
空欄の扱いチーム・Subチームの空欄は空文字として同一視する。- や なし は別の値
所属部門重複キーに含めない
手動登録の重複エラーで拒否する（上書き確認は出さない）
取込の上書きprojectId を維持し、所属部門・名称・項目ID を更新する
取込の必須エラー顧客・案件が空欄の行が 1 行でもあればファイル全体を中止する
ファイル内重複ファイル全体を中止する

14.2 未確定の確認ポイント

  1. 稼働表の行削除は「表示対象から外すだけで、過去の割当は保持」でよいか
  2. 要員マスタ削除は、その年度の割当がある場合ブロックしてよいか
  3. 部門名の重複を許容するため、部門選択肢の表示を「部門名（部門ID）」に変更してよいか
  4. 割当は「1人要員・1週に1プロジェクト」の前提でよいか
  5. 割当がある行の社員番号変更はブロックし、行削除→行追加を案内する案でよいか
  6. マスタに無い社員番号を入力した場合、行を空のまま残すか、行自体を削除するか
