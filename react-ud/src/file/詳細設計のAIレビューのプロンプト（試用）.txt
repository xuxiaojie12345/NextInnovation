详细设计Review提示词：
1.详细设计格式和结构的确认：
	1.1 文件名是否以[模块功能名]_詳細設計.md的形式命名的
	1.2 详细设计是否包含以下几个模块：
		1. 背景，2. 画面参数定义，3. 业务逻辑与校验规则，4. 接口定义，5. 异常处理，6. 实现注意事项
	1.3 作成者和作成日是否记载
2.画面参数定义确认：
	2.1 提示词中记载的所有项目是否在画面参数定义中全部包含，每一个项目是否明确记载以下定义信息：
		项目定义包含：项目名，种别，必须，MaxLength，I/O，許容文字 (Allowed Chars)，文字配置 (Align)，初期値 (Default)，表示制御 (Control)，备注。
	2.2 如果存在pull-downList项目，pull-down需要的数据来源是否明确记载。
	2.3 提示词中记载的必须入力项目是否在详细设计中明确记载
3.业务逻辑与校验规则确认
	3.1 提示词中记载的所有功能在详细设计中是否全部包含
	3.2 详细设计中各功能的处理流程是否和提示词中记载的一致
	3.3 提示词中记载的check处理在详细设计中是否全部包含
	3.4 详细设计中各check进行的时机是否正确，错误信息以及错误信息类型是否与提示词中记载的完全一致
	3.5 Zod校验的时机以及处理是否正确，出现错误时的message是否和提示词中记载的一致
4.API接口定义确认
	4.1 API接口的定义是否和提示词中记载的一致，提示词中记载的参数是否全部包含。
		定义包含：API名，功能，Method，Endpoint
	4.2 Request/Response的形式是否和下面例子的记载形式保持一致。
	    Request的形式例：
	    {
	      "Template File": "aaa.txt",
	      "Market": "JPN"
	    }
	    Response的形式例：
	    {
	      "code": 200,
	      "data": [画面需要的数据],
	      "message": "success"
	    }
	4.3 Response关于成功和失败时的定义是否完整。
	    Response成功时的定义例
	    {
	      "code": 200,
	      "data": [画面需要的数据],
	      "message": "success"
	    }
	    Response失败时的定义例
	    {
	      "code": 401,
	      "data": null,
	      "message": "faile"
	    }
5.异常处理正确
	5.1 异常处理的时机是否正确，
	5.2 是否包含网络断开/超时和服务器内部错误异常
	5.3 各异常的处理方式以及返回的错误信息是否明确记载
6.其他确认
	6.1 文档结构规整、描述简洁准确，符合阅读习惯，易于使用者理解把握业务逻辑与处理规则
