4. 处理流程
   【AuthenticationApi】
    4.1 客户端通过POST请求访问接口 /api/authentication，将username、password等请求参数，以JSON格式发送至后端服务。

    4.2 后端【AuthenticationController】接收前端请求，通过【LoginRequest】实体对象封装并校验请求参数，完成请求入口层的参数接收与初步格式验证。

    4.3 控制器层调用【AuthenticationService】接口中的 login() 方法，将校验后的请求对象传递至业务逻辑层处理。

    4.4 【AuthenticationServiceImpl】业务实现层执行核心登录逻辑：
        • 对请求参数进行非空、长度、格式等合法性校验
        • 校验不通过则直接返回参数异常响应

    4.5 业务层通过【UD01Mapper】数据访问层，根据username和password查询数据库中的用户信息，获取用户实体对象。

    4.6 登录核心验证逻辑：
        • 判断用户是否存在，不存在则返回"账号不存在"
        • 密码错误则返回"密码不正确"

    4.7 验证全部通过后：
        • 将完整用户信息存储到Session，key为'currentUser'
        • 构建登录成功响应体，包含用户基础信息

    4.8 封装【LoginResponse】响应对象，统一返回标准格式：
        {
            "code": 200,
            "msg": "登录成功",
            "data": {
                "userid": "xxx",
                "username": "xxx",
                "responsible": "xxx",
                "userposition": "xxx",
                "email": "xxx"
            }
        }

    4.6 直接返回 DocumentType 对象数组（List<DocumentType>），不包含外层 code/data 包装。
    响应示例：
    [
      {
        "doctype": "string",
        "description": "string",
        "registerDatetime": "2024-01-01T00:00:00",

    4.4 【UD07ServiceImpl】业务实现层执行核心查询逻辑：
        • 根据SERIE和CHNR关联查询HDOC_REC_DATA_OM、HDOC_REC_DATA_VDA_GENERAL、HDOC_REC_DATA_VDA_VARIANTS、HDOC_REC_DATA_KOLA_VARIANT表，获取Model、Built week、Product type、VIN、Country of Operation、SYMBOL_STR、DESCRIPTION、S-Note NO。
        • Engine no固定值"A01"设定。
        • SYMBOL_STR处理——取Symbol先頭から8桁まで取得。8桁不足の場合、左寄せ半角スペースで補足。
        • 排序处理——按FUNCTION_GROUP（左寄せ半角スペースで4桁まで補足）＋ FAMILY_ID（3桁）排序。

    4.5 封装响应对象，返回车辆规格信息。

        • 接收前端传递的搜索条件（字段值及运算符）
        • 支持12个字段的检索条件（Product class、Number、Market、Variable、Value、VS、VS2、Comments、Add、Delete、Created by user、Date）
        • 每个字段可单独指定运算符（= 或 !=）
        • Number、Date字段额外支持 >、< 比较运算符
        • 根据条件从HDOC_USER_DEFINED_RULES表动态查询
        • 等值字段用 = 或 != 匹配，字符串字段用 LIKE 或 NOT LIKE 匹配
        • 返回匹配的全部记录列表
